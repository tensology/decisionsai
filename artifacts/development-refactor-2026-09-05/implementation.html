Backend ownership and contracts

distr/gui/web/routes/development/ registers feature routes at their existing public URLs. Development logging no longer imports through Settings, removing the import cycle exposed by a fresh route-registration test.

Boundary Canonical implementation under distr/
Plan core/planning/service.py owns revisions and discovery. files.py owns recoverable file projection. Feature routes expose workspace, item and file-review operations.
Incoming core/incoming/service.py owns linked incoming conversations and snapshots.
Terminals core/terminals/service.py and existing terminal runtimes. Routes still register through Projects for URL compatibility.
Automations Existing core/automation/ engine. schedule_import.py owns lossless translation; scheduler owns durable dispatch claims and acknowledgement.
Reports core/reports/service.py combines recent workflow, automation and standalone execution records. routes/development/reports.py exposes a bounded read-only query.
Workflows and threads Separate definition, step, execution, thread, control and tool routes call existing domain services. Some execution route files remain large.

Dependency rules

  • Features own their view state, requests, handlers and cleanup. Connections use declared callbacks and context rather than imports of sibling implementations.
  • Project identity, board identity and thread identity stay distinct. Multiple boards may share one project. A thread keeps its board scope.
  • The shell still supplies live context getters and selected setters. This is an explicit integration boundary, not complete state isolation.
  • Thread and Reports requests are cancelled or ignored after navigation. Terminal polling and thread sockets stop when their view closes.
  • Keep model selection behind common helpers and existing execution adapters. No framework change or separate microservices were introduced.

Correctness changes

Plan integrity

Failed saves retain the draft and block unsafe navigation. Revision and workspace checks reject stale or cross-workspace edits. Changed approved content becomes a draft while approval history remains. Mobile item selection and delayed navigation are covered.

The database revision and a pending file write commit together. File projection follows the commit and retries on workspace reopen. Commit failure leaves the old file intact. Rename failure keeps the committed revision recoverable. External changes are checked before writing and retained for review.

File review compares the saved/editor version with the project file. Import requires the reviewed revision and file hash; restoring a missing file retains an unsaved editor draft. Discovery preserves curated overviews and creates proposals instead of replacing them. Unchanged discovery does not add revisions. The language input now describes its actual template, append and scan capabilities.

Dispatch and navigation

Automation imports select an exact or nearest containing project and reject ambiguous multi-project scope. Unsupported recurrence features are reported per source instead of silently changing the schedule. Supported cron monthly days and time zones are preserved.

Scheduled occurrences have a durable dispatch attempt before work starts. The schedule advances only after acknowledgement. Failed or ambiguous dispatch pauses for manual review, including after restart. Concurrent schedule edits survive acknowledgement. This avoids blind retries that could duplicate work.

Queued commands query queued rows directly, preventing delivered rows from starving the next command. Idle timers pause even if a worker never produces its first response. Late thread loads cannot restore an obsolete URL. Empty workflows and agent steps without instructions cannot start through the Development controls.

Independent surfaces

Catalog sources fail independently. Distinct boards sharing one project remain visible. Automation history stays with its selected record. Reports has real history, source/status filters, retryable errors and a mobile scrollable table. Accepted dispatch bookkeeping is excluded from the report to avoid presenting it as an additional execution.

Verification and remaining work

Verified locally

The final selected backend suite passes 160 tests across 20 modules. It covers public route registration, reports, Plan persistence and reconciliation, schedule fidelity, dispatch claims/recovery, controls, boards, tickets, terminals and existing workflow behavior. Existing deprecation warnings remain.

All 94 browser tests pass against the real templates and JavaScript with fixture APIs. Coverage includes section navigation, save failures, delayed responses, workflow editing, tickets, terminals, automation controls, file review and Reports at desktop and mobile widths. Final counts and evidence are recorded in verification.json, backend-results.xml and browser-results.xml beside this report.

The fixture server runs independently from the desktop runtime and does not start its database, scheduler or agents. These tests do not certify live provider calls or external connector availability. JavaScript/CSS parsing, local module resolution and diff checks accompany the regression suites.
