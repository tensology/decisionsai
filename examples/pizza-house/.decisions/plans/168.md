## Why this ticket exists (brief)

Ticket #168 closes the gap between a working prototype and a deployable restaurant site. The MVP codebase already renders pizzas from data, toggles mobile nav via `aria-expanded`, has responsive breakpoints, validates the form before submission, and opens a pre-formatted `mailto:` with cart contents. What's missing to be "done" is:

1. The site still uses inline SVGs and lacks SEO/brand basics (manifest, favicon file, meta description).
2. A few viewport sizes need visual verification — the 3-col grid at small widths collapses but no width between 700–800 px was explicitly checked.
3. Order-flow UX feedback is missing a "thank you" confirmation state that doesn't depend solely on the OS mail client returning.

No new features (menu categories, dietary tags, payment gateway). Stays inside "restaurant landing page with maintainable menu and validated journey."

## Implementation slices (ordered)

### Slice A — Make it deployable
- Create `favicon.svg` (matches existing data URI icon in `<head>`), drop it alongside the HTML.
- Add meta tags to the `<head>`: `description`, `og:title`, `og:description`, `twitter:card`.
- No new files beyond `favicon.svg`; no backend additions yet.

### Slice B — Validate responsiveness at every major breakpoint + a real image path pattern
- Confirm breakpoints hold across three viewports (explicit, documented widths): 600 px / 750 px / 840 px / 1200 px. The site already ships with `800px` and `700px`, so this slice is audit-and-patch, not reinvent the grid — only add a `900px` break if an element refuses to sit cleanly at one existing stop.
- Replace each inline SVG placeholder in `app.js` pizza objects with relative `src="images/{id}.webp"` paths and ship four WebP images (`ember.webp`, `market-green.webp`, `karoo-mushroom.webp`, plus any new pizzas added to the data). Keep current inline SVGs as a fallback via the data attribute — see Slice E.

### Slice C — Hardened order flow (client only)
- Currently: form submits → empty-cart check → opens `mailto:` link with pre-filled subject/body. Works, but there is no *visible* confirmation for users who block mailto links or have no desktop client configured.
- Action: on successful submit with valid form + non-zero cart, show a brief in-page "Thank you — your order email was prepared" state (non-blocking toast), then the `mailto:` fires as before. The new confirmation is *informational only* and does **not** replace an eventual backend endpoint.
- Existing JS:
  - `getCartTotal()` returns sum via `formatPrice()`.
  - `checkoutForm.addEventListener("submit",...)` already calls `reportValidity()` and refuses on empty cart — that stays in place verbatim; the only change is what comes after it fires.

### Slice D — Light audit pass (accessibility + performance)
- Add `<img decoding="lazy"` to rendered cards (already `loading="lazy"`, so no change needed).
- Ensure all `aria-label`s on quantity buttons are unique across slices if pizzas multiply — current pattern already names each button; only verify it when data changes.
- Lighthouse-friendly: site has correct viewport, CSS custom properties from `:root`, skip-link working, contrast check is not being broken by added text (default palette is good).

## Tests / acceptance criteria
- Viewport widths `600`, `750`, `840`, `1200` px all render without horizontal overflow.
- Menu grid renders from the data array — edit one pizza price in JS and the cart subtotal updates (confirm by clicking `+`).
- Empty cart + submit shows feedback text (unchanged), does **not** open mailto, focus stays on form.
- Valid order submits: in-page "thank you" toast appears for ≥2 s; then `mailto:` link is triggered. Open Chrome DevTools → Console → no errors.
- No `loading="lazy"` attributes are removed (lazy loading remains).
- A screen reader sees each pizza as a `<article>` listitem with distinct `aria-label`s on the quantity buttons — confirmed visually by reading through the DOM in DevTools accessibility panel.

## Rollback / de-risk

- **Rollback:** all code changes touch files already tracked under git at HEAD (`index.html`, `styles.css`, `app.js`) plus new lightweight assets in `images/` and `favicon.svg`. A single `git reset --hard HEAD` reverts the site to its last deployed state with zero data loss because no server-side state is introduced. The plan's de-risked ordering flow change can be narrowed by replacing just one statement (the toast insertion) rather than restructuring JS, which limits blast radius.
- **De-back out any single slice:** each slice touches at most 2 files and can be `git revert`'d independently:
  - Slice A → `index.html` + new `favicon.svg`.
  - Slice B → add CSS breakpoint or replace SVG source (keep inline SVGs in data array, just comment out).
  - Slice C → remove the three toast lines after successful submit; keep the existing mailto logic.
- **What would break:** if you ship without replacing the inline SVG `src` with real WebP images, no functionality breaks — the site still loads. The only "broken" piece is that placeholder SVGs are visually generic; the ticket allows shipping them as-is for now since we're not adding a new delivery pipeline (no payments).
- **Risk of scope creep:** if anyone suggests a backend submission endpoint (Netlify Form, Vercel webhook), that's Ticket #169 territory — out here.
