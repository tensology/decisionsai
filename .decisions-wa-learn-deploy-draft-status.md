## What was built

### 1) Verification learning
- After completed WA work, Telegram opens a **verification** gate (`wv:<token>:ok|redo`, waiting_kind=`verification_review`).
- Negative judgments (`this is shit`, `wrong`, `redo`, free-form critique) call `record_verification_lesson`:
  - run steering via `record_run_steering_feedback` (`event_type=changes_requested`, `rule_type=verification_lesson`)
  - durable board learned rule via `record_learning_signal` (`enabled=True`, `promote_after=1`)
- `verification_lessons_context(board_id)` surfaces lessons on the next similar ticket’s verification prompt.
- Rejected verification **blocks** deploy assist and client draft.

### 2) Deploy assist gate
- After **Looks good**, Telegram asks Production vs Development (`wd:<token>:prod|dev`, waiting_kind=`deploy_assist`).
- Suggestion is heuristic from title/summary/contact (`suggest_deploy_target`) — **nothing is deployed**.
- Decision stored as `deploy_status=settled`, `deploy_target=production|development`.

### 3) Client draft gated on deploy settled
- `prepare_completed_reply` returns `None` until `deploy_status=settled`.
- Only then: compose draft + Send / Revise / Leave draft (`wa:…`), dry-run respected.
- Dispatcher + CLI success path use `notify_post_completion` (verify first).
