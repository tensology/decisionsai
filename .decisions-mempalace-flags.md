## Surface recommendation: **both** (chat + Development), chat-primary for semantic reads

Paul asked: agent chat, Development thread, or both?

**Recommend: both**, with different roles:

| Surface | MemPalace role when flag ON | Why |
|---------|----------------------------|-----|
| **Agent chat** (OpenAI gpt path via `OpenAILLMService` → `core_mixin`) | **Primary semantic consumer** — RAG inject + markdown dual R/W + memory tools still on files | Chat already auto-queries RAG per turn and exposes MEMORY.md tools; biggest user-visible win |
| **Development / harness / CLI** | **Dual-write + orchestrator prefer-read**; FS companions stay the ticket/CLI pickup surface | Dev threads already inject orchestrator SQL + workspace handoff/pickup; palace adds searchable verbatim without replacing FS |

Do **not** make MemPalace the sole Development pickup store yet — `~/.decisions/workspaces/**` remains operational projection (handoff/ledger/active).

### How memory is consumed TODAY (citations)

#### Chat agent (OpenAI / gpt compatible path)

1. **System prompt — developer/orchestrator slice**  
   `distr/core/agent/services/llm/core_mixin.py` → `_build_system_prompt_template` (~L1606–1669) calls `build_developer_context(chat_id=…).to_prompt_text(max_chars=2200)`.  
   That assembler pulls orchestrator SQL via `DeveloperContextAssembler._fetch_user_memory_context` → `orchestrator_memory.build_memory_context` (`developer_context.py` ~L870–891; `orchestrator_memory.py` ~L747+).  
   OpenAI provider is thin (`providers/openai.py`) and inherits this mixin path.

2. **Per-turn RAG inject**  
   `core_mixin._maybe_inject_rag_context` (~L854–902), invoked on user message generate (~L2024): MemPalace `prefer_read_rag_context` when flag ON, else LlamaIndex `query_rag` against `./llama_index_storage`.

3. **Markdown memory tools (AGENT/USER/MEMORY/EVENTS.md)**  
   Registered in `agent/tools/loader.py` (`MemorySearchTool` / `MemoryReadTool` / `MemoryAddTool` / `MemoryEditTool`) → `agent/tools/system/memory_tools.py` → `distr/core/memory/files.py`.  
   Dual-write / prefer-read hooks live in `files.append_markdown_section`, `append_events_text`, `load_context_snippets_for_llm`.

4. **Initiative (not every chat turn)**  
   `distr/core/initiative/context.py` → `_fetch_memory_snippets` (~L185–200) calls `load_context_snippets_for_llm()` for AGENT/USER/MEMORY.md.

Chat does **not** auto-inject full MEMORY.md into every turn; it uses tools + initiative + RAG + the developer_context orchestrator slice.

#### Development thread / harness / CLI

1. **Developer context packet**  
   `developer_context.DeveloperContextAssembler.build` → `_fetch_user_memory_context` (orchestrator SQL) + `_fetch_workspace` → `workspace_memory.reader.load_workspace_context` (handoff/pickup/ledger FS under `~/.decisions/workspaces/`).

2. **Workflow runs**  
   `workflow/dispatcher.py` (~L1790+) builds/scopes `run_data["developer_context"]` from `build_developer_context()` for harness steps.

3. **Ticket → CLI**  
   `kanban/ticket_cli_context.build_kanban_ticket_cli_instruction` + `ticket_cli_memory` / pickup_handoff for enrichment briefs; companion FS remains the pickup surface.

4. **Steering**  
   `workflow/steering_memory.py` dual-writes to MemPalace room `steering` when flag ON (legacy run_data.steering_log stays).

Development does **not** currently read `models/memory/*.md` or LlamaIndex RAG on the harness prompt path; those are chat/initiative surfaces.
