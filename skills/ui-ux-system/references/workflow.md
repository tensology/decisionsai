# UI/UX audit, design and verification

Use this sequence for a whole frontend or a change that spans screens. For a bounded change, apply the stages to its affected states and routes. Read the specialist for the choice you are making.

1. **Assess the existing experience.** Use `ui-ux-system` and `better-interface`. Inventory routes and shared components. Open them with representative content at narrow, tablet and desktop widths. Capture full-size baselines and record the task affected, the visible issue and its severity. For an existing brand, record the approved palette, actual font files and weights, and examples of how the colors and type were used. Compare the running site to those references before changing tokens.
2. **Validate the flow and placement.** Use `product-design` for user jobs, next actions, states and recovery. Use `better-layout` for ordering, grouping, grid, measure and spacing. Sketch mobile and desktop in reading order. Place the next action alongside its context and align common edges first. Remove wrappers that duplicate a group or create dead space. Check that each state has a clear next step. Write observable acceptance criteria for the issues from stage 1.
3. **Implement and review.** Preserve approved behavior and content. Fix shared shell or tokens where they cause several symptoms, then the route-specific issues. Use `better-interface` to review the rendered hierarchy. Consult `web-ux-patterns` when choosing an interaction pattern. Use `web-design-guidelines` for implementation checks. Use Impeccable only when explicitly invoked, after placement, for responsive adaptation and polish. Use Apple Design when the task calls for Apple platform conventions. Specialist advice yields to approved references and tested user flows.
4. **Verify the result in a real browser.** Use `ui-verification` for scoped measurements and `ui-validation` or the project's browser suite for complete journeys. Repeat the baseline with the same content and viewport conditions. Inspect each changed screen and meaningful state individually at readable size. Check real clicks and keyboard focus, mobile hit areas, content wrapping, scroll, images and fonts. Cover the happy path and an applicable empty, error or recovery path. Use disposable data for write paths. If an issue remains, fix it and repeat the affected checks.

Record the old and new screenshots, the task steps and outcomes, the exact viewports and environment, and any blocked checks. A design review answers whether placement and hierarchy suit the task. Browser verification demonstrates what the implementation actually does.
